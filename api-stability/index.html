    Public API stability¶

    RigorFoundry inventories every name in the package-level rigor_foundry.__all__ under API-stability schema 1.1. The authoritative machine-readable inventory is returned by:

    from rigor_foundry.api_stability import public_api_manifest

manifest = public_api_manifest()

    The broader 1.0 Python, CLI, and serialized-schema boundary is exposed by rigor contract and documented in the 1.0 stable compatibility contract. Source metadata declares package version 1.0.0. The manifest describes compatibility; release authorisation and registry availability require separate evidence.

    The result has sorted stable and provisional name arrays, exact stable runtime-binding records, and structured deprecated records. Compatibility tests require every top-level export to have exactly one classification. Every stable binding is also checked for its exact canonical object identity, object kind, implementation module, and qualified name, so retaining or spoofing a spelling while rebinding it fails.

    Stable imports¶

    The current stable top-level import names are:

    • AuditPolicy
    • AuditReport
    • Candidate
    • GitTrustPolicy
    • ReviewRecord
    • __version__
    • report_markdown
    • review_templates
    • scan_repository
    • stable_contract_manifest
    • validate_reviews

    AuditPolicy is implemented by the cohesive policy_models owner, while the established rigor_foundry.models.AuditPolicy import and runtime module identity remain unchanged. This split is an internal ownership change, not a public API migration.

    Within the same major release, these names will not be removed or silently rebound to an incompatible kind of object. Record fields and serialized protocols retain their own explicit schema/version contracts; stable import availability does not erase those migration boundaries.

    Provisional imports¶

    report_sarif, SARIF_SCHEMA_URI, and SARIF_VERSION are provisional public imports. Their emitted document is independently governed by SARIF 2.1.0 and the explicit RigorFoundry property names documented in SARIF export.

    RuleMaturityPolicy, RuleReviewEvidence, RuleMaturityAssessment, RuleMaturityReport, RULE_MATURITY_SCHEMA_VERSION, MATURITY_CASE_MANIFEST_SCHEMA_VERSION, and evaluate_rule_maturity_manifest are provisional. Their JSON contracts are independently versioned at schema 1.0, and enforcement consumes their exact content digest rather than treating top-level import stability as protocol compatibility.

    ExternalSourceClaim, SourceRetrievalPolicy, SourceCapture, SourceVerification, SOURCE_PROVENANCE_SCHEMA_VERSION, read_source_payload, source_provenance_to_json, and verify_external_source are provisional. Their schema 1.0 records distinguish declared retrieval metadata from publisher authority and bind claim, policy, capture, and successful offline verification through separate digests.

    VerificationBundle, EvidenceEntry, DetachedEvidenceSignature, ReviewEvidence, ModelAliasEvidence, OfflineTrustPolicy, VerificationKeyPolicy, EvidenceVerificationResult, OfflineVerificationReport, verify_evidence_bundle, and their schema/domain constants are provisional Python imports. The installed rigor verify command and its schema-1.0 bundle/trust-policy/result contracts form the stable offline-verification CLI boundary. See Offline evidence verification. The v1 verification-key wire remains closed and unchanged. Explicitly supplying enrolled_identity selects a separate v2 key record for semantic signing roles; its identity is included in the key-policy digest. Existing semantic_reviewers policies containing v1 records are refused by the five-role builder. Reissue those records with selected identities and update their changed policy digest in the host's expected selection. Construct RuleChainV2TrustRoles through its keyword builder: the author policy is a new required role, and positional dataclass construction is not a migration route.

    The module-level signed_clause_semantics_set_v2.SignedClauseSemanticsSetV2 parser and verifier are provisional Python APIs. They authenticate an exact semantics body with separate author and reviewer signatures without granting adoption or effect authority. See Canonical clause semantics.

    The module-level clause-semantics binding, constraint-evaluator registry, authority-requirement and owner-confirmation APIs are provisional. The binding retains the current digest-only authority-clause wire. Native ratification-source verification supports the explicitly selected Claude JSONL format and produces an integrity-only proof. None of these APIs adds a stable package-level export or effect-admission authority. See Canonical clause semantics.

    The module-level rule_chain_candidate.inspect_rule_chain_candidate and RuleChainCandidateReport are provisional read-only Python APIs. They are not package-level exports in the frozen 1.0 compatibility inventory and do not admit a selected lock or an effect. See Rule-chain candidate inspection.

    Every other current rigor_foundry.__all__ name is explicitly provisional. These APIs remain typed, documented where public, and covered by production-boundary tests. A minor release may refine or remove a provisional import after an explicit changelog entry. Any independently frozen serialized protocol retains its own compatibility and migration requirements.

    The module-level signed-acceptance, v2 candidate, effective-lock, selected-chain and selected-semantics APIs are also provisional. Their full runtime dependency chain is documented in Rule-chain candidate inspection and Canonical clause semantics. They add no package-level exports or stable CLI dispatch path. Existing v1 pack/profile/lock wires and the current digest-only AuthorityClauseV2 remain unchanged.

    The module-level condition_facts.ConditionFact, ConditionTruth and condition_evaluation.evaluate_condition_state APIs are provisional. They evaluate supplied known, absent and unknown observations without changing the existing ConditionExpression1.1 Boolean behavior. The provisional module command python -m rigor_foundry.condition_evaluation_cli uses its own explicit operand/result versions and is outside the frozen rigor1.0 command inventory. It never authenticates fact provenance or grants effects. See Conditions with partial observations.

    Compatibility requires explicit selection of the new signed acceptance and host-state records. Identity-bearing reviewer key enrollment must agree with its identity binding; case aliases cannot occupy separate reviewer bindings. The existing semantic-source proof wire retains its fields: the new consumer checks the nested discovery selection on its held source state. The interim scope resolver explicitly refuses profiled registries instead of interpreting their layout with fixed v1 paths. Path-root derivation uses the explicit roots in either canonical registry schema.

    Consumers that need a provisional name should pin an exact RigorFoundry version and test the relevant schema or behavior rather than inferring compatibility from package import success.

    Deprecation contract¶

    A stable name must remain exported while deprecated. Its lifecycle record must name:

    • the final semantic version that introduced the deprecation;
    • a different classified replacement, when one exists; and
    • a final semantic version no earlier than two minor releases later within the same major line. A new major version may perform the removal explicitly.

    Compatibility tests reject duplicate or overlapping classifications, unclassified exports, classifications for absent names, non-final semantic versions, self-replacements, missing replacements, and a too-short same-major deprecation window. There are no deprecated stable top-level imports in the frozen 1.0 contract.

    The module-level policy source APIs documented in Policy source bytes are provisional. Their explicit budget, span and region records use schema1.0 with distinct object kinds. They check supplied input integrity and byte accounting; semantic acceptance and trusted host admission require their separate owning consumers. These imports do not extend the frozen package-level API or installed command inventory.

    The module-level task-definition, context-producer-contract, repository-state and inline repository-inventory APIs described in Context source models are provisional. Their schema1.0 identities bind descriptive source data; they do not install producers or extend the frozen package-level API or installed command inventory.

    The fixed typed-reference/source-parser, retained source-lifetime and owner observation/proof APIs documented in Retained context sources are provisional module imports. Their explicit schema1.0 records and independent preimages preserve source integrity without granting installed producer or operation authority.

    The host-composed task and registry readers and complete implementation observations described in Task and registry source owners are provisional module imports. They verify actual retained source values and do not grant enclosing host or effect admission.

    The module-level repository Git input observation API is provisional. Its complete Git preimages preserve baseline identities and unresolved index stages. It does not extend the frozen package exports or establish maintained-inventory completeness or an atomic filesystem snapshot.

    The module-level repository file input API is provisional. It adds actual baseline/current file-byte identities within the observed Git path domain. Unknown types and language/role remain explicit; configured-root completeness and authenticated context ownership are separate.

    The configured inventory domain parser, path classifier and retained-source Git-root observer are provisional module imports. The new inventory-domain/1.0 source pair has a fixed owning parser; other producer classes retain their existing format restrictions. No complete inventory, context, root-package export or effect-admission result is added.

    The complete declared-root collector, current-directory observer, shared row classifier and fixed retained-domain selection described in Configured inventory inputs are provisional module imports. They preserve all original root observations and explicit namespace ownership, without extending frozen exports or authenticating a maintained inventory.
