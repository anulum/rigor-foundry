    Rule catalogue¶

    This catalogue lists all 68 registered rules, grouped by category, with the fixed rationale and verification guidance each detector attaches to its candidates. SARIF rule helpUri values point at these sections.

    A RigorFoundry result is an audit candidate for evidence review, never a defect verdict; only a validated review record decides it.

    test-authenticity¶

    TA001-test-double¶

    Test-double API or fixture signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A test double may replace the production boundary that the test claims to prove.

    How to verify. Trace the test from its public API, CLI, adapter, or workflow entry point; verify that the substituted object is an approved protocol-faithful external fixture and that the production adapter and validation path still execute.

    TA002-synthetic-fixture¶

    Synthetic fake, stub, dummy, or toy naming signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Synthetic naming can identify fixtures that do not represent a real contract.

    How to verify. Compare the fixture with the repository schema, external protocol, recorded artefact, or documented domain example and prove which production boundary consumes it.

    TA003-skip-or-xfail¶

    Skipped or expected-failure test signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A conditional or ignored test can hide an unverified production path.

    How to verify. Reproduce the dependency or hardware boundary, verify the gate is explicit and fail-closed, and identify the separate real integration job or evidence path that executes the contract.

    TA004-coverage-exclusion¶

    Coverage exclusion signal in tracked Python or JavaScript-family text.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Coverage exclusions can conceal reachable error or integration paths.

    How to verify. Prove the branch is structurally unreachable on every supported runtime or replace the exclusion with a real error-path or matrix test.

    TA005-lint-suppression¶

    Local lint or security suppression signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A local suppression may hide a policy or security defect.

    How to verify. Run the owning analyser without the suppression, establish the exact diagnostic, and verify a tracked, source-specific justification or remove the suppression.

    TA006-type-suppression¶

    Local static-type suppression signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A type suppression can hide a broken production or test contract.

    How to verify. Run strict typing on the owning module, confirm the exact error code and external typing boundary, then replace the suppression or document the narrow tracked reason.

    TA007-module-injection¶

    Module-resolution injection signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Module injection can bypass import, packaging, or optional-dependency wiring.

    How to verify. Execute the real package or direct-script import path in a clean subprocess and prove the same packaging and dependency boundary without replacing module resolution.

    TA008-coverage-bucket-name¶

    Non-specific test-owner name signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. The test owner name suggests a cross-module coverage bucket.

    How to verify. Map every test to one production module or one named integration contract and split unrelated behaviours into their owning test surfaces.

    TA009-unparseable-python-test¶

    Tracked Python test cannot be parsed.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. An unparseable tracked test cannot be structurally audited.

    How to verify. Run the supported Python parser and repair or remove stale test code.

    TA010-smoke-only-test¶

    Test has no local behavioural contract signal.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. The test exposes no local assertion, exception, or behavioural helper call.

    How to verify. Identify the observable production regression this test catches and add an explicit result, state, persistence, error, or integration contract.

    TA011-private-production-surface¶

    Test directly reaches an underscored first-party surface.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. The test directly reaches an underscored first-party production surface.

    How to verify. Run the behaviour through the public API, CLI, adapter, pipeline, or documented internal contract and prove that the private call is not bypassing that boundary.

    architecture¶

    AR001-first-party-import-cycle¶

    Non-trivial first-party Python import cycle.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A first-party import cycle can invert ownership and obscure initialisation.

    How to verify. Trace runtime import order and public ownership for every edge; dismiss only if the cycle is type-only or otherwise absent from the production execution graph.

    AR002-wildcard-import-boundary¶

    Wildcard Python import boundary.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A wildcard import hides the explicit API and dependency boundary.

    How to verify. Enumerate the intended compatibility exports, downstream consumers, and generated API ownership; replace with explicit lazy or static exports unless the facade contract is documented and drift-gated.

    AR003-broad-optional-import-boundary¶

    Import guarded by a broad exception handler.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A broad import guard can mask dependency defects as optional absence.

    How to verify. Run the real import with the dependency present, absent, and broken inside its package; catch only the expected absence and surface nested failures.

    AR004-executable-facade¶

    Facade also owns executable function bodies.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A compatibility facade also owns executable function bodies.

    How to verify. Classify every body as import/lazy-export plumbing or independent execution; extract mixed lifecycle or algorithm ownership behind the stable facade.

    AR005-no-module-named-test-owner¶

    Production module lacks an obvious module-named test owner.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. The production module has no obvious dedicated module-named test owner.

    How to verify. Search integration and public-contract tests for this module's actual production surface; either record the named owner or add a dedicated real-surface test.

    AR006-duplicate-python-implementation¶

    Exact non-trivial top-level Python implementation body has multiple owners.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Multiple first-party functions own an exact non-trivial implementation body.

    How to verify. Confirm whether the definitions are intentional independent protocol adapters, generated outputs, or duplicated ownership; consolidate only when dependencies and public identities permit it.

    AR007-relative-dependency-cycle¶

    Non-trivial relative dependency cycle in a non-Python language surface.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Relative dependencies form a non-trivial cross-file cycle.

    How to verify. Trace build/runtime direction and generated ownership for every edge; break mixed lifecycle or inverted dependencies while preserving public API/ABI.

    AR008-no-polyglot-test-owner¶

    Non-Python production owner lacks an obvious source-named test owner.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. The production owner has no obvious dedicated source-named test surface.

    How to verify. Trace language-native unit tests and cross-language parity/integration tests; record the real owner or add a dedicated public ABI, FFI, or executable contract.

    godfile¶

    GF001-large-responsibility-owner¶

    Tracked code owner exceeds its review threshold.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. The file exceeds the configured review threshold; line count opens a responsibility audit but is not itself a GodFile verdict.

    How to verify. Read the full file, classify each top-level responsibility and direct dependency, trace every public consumer and test owner, then record one cohesive responsibility with a reopen trigger or split mixed ownership behind stable contracts.

    GF002-missing-size-registry¶

    Configured module-size registry is unavailable.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Configured GodFile responsibility evidence cannot be loaded.

    How to verify. Restore the tracked registry and rerun its native strict audit.

    GF003-invalid-size-registry¶

    Configured module-size registry is malformed.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Configured GodFile responsibility evidence is malformed.

    How to verify. Run the repository-native module-size registry parser and repair it.

    GF004-incomplete-size-decision¶

    Module-size decision lacks required evidence.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A large-file decision lacks required responsibility evidence.

    How to verify. Read the complete owner and record current responsibility, direct dependency boundary, exact line count, disposition, and reopen trigger.

    GF005-size-decision-drift¶

    Module-size decision differs from the tracked tree.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A reviewed large-file decision no longer matches the tracked tree.

    How to verify. Re-read the complete file, re-evaluate its responsibility/dependencies and reopen trigger, then update the registry only after that review.

    governance¶

    GV001-missing-repository-audit-policy¶

    Repository-specific audit policy is absent.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Repository-specific audit ownership is missing or ambiguous.

    How to verify. Read the repository rules and canonical internal TODO, then define the exact roots, packages, GodFile registries, and enforcement state without copying another project's assumptions.

    GV002-unscanned-tracked-code¶

    Tracked code or test content could not be parsed as bounded UTF-8 text.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A tracked code or test path was outside the scanner's parsed scope.

    How to verify. Inspect the Git object and worktree path directly, establish whether it is an intentional symlink/submodule/binary/generated owner, and configure a specific auditor; a clean claim is forbidden while the path remains unexplained.

    GV003-undeclared-audit-domain¶

    Mandatory audit domain has no repository applicability decision.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. Repository-specific audit ownership is missing or ambiguous.

    How to verify. Read the repository rules and risk model, then declare the domain required or justify not-applicable with repository-specific evidence.

    GV004-uncontrolled-required-domain¶

    Required audit domain has no active portable rule or required native adapter.

    Introduced in rigor-foundry/1.0.0.

    Why it matters. A required quality domain cannot support a repository conformance claim without a portable rule or required native adapter.

    How to verify. Read the domain threat/risk model, wire a real time-bounded repository audit or justify not-applicable with repository-specific evidence; do not copy a control name that does not exercise this codebase.

    GV005-unscanned-jupyter-notebook¶

    Tracked Jupyter content could not be completely projected into Python-AST analysis.

    Introduced in rigor-foundry/1.18.0.

    Why it matters. A tracked Jupyter notebook could not be completely projected into the bounded Python-AST analysis surface.

    How to verify. Open the exact tracked blob, validate nbformat 4 and an unambiguous Python language declaration, repair malformed or unsupported cells, and rerun the read-only scan.

    GV006-unscanned-github-actions¶

    Tracked GitHub Actions YAML could not be completely analysed.

    Introduced in rigor-foundry/1.19.0.

    Why it matters. A tracked GitHub Actions owner could not be completely analysed.

    How to verify. Read the exact tracked blob, resolve the bounded parser or structural limitation, and rerun. An unexplained incomplete owner cannot support a clean claim.

    application-security¶

    AS001-dynamic-code-execution¶

    Dynamic code execution through eval or exec.

    Introduced in rigor-foundry/1.2.0.

    Why it matters. eval and exec run arbitrary code and turn any tainted argument into execution.

    How to verify. Trace the argument to a trusted literal or a validated allow-list; otherwise replace the call with an explicit parser, dispatch table, or sandboxed evaluator.

    AS002-shell-command-execution¶

    Shell command execution surface via shell=True, os.system, or os.popen.

    Introduced in rigor-foundry/1.2.0.

    Why it matters. A shell command surface lets a tainted argument inject additional commands.

    How to verify. Pass an argument vector without a shell (shell=False, or subprocess with a list), or prove every interpolated value is a trusted constant.

    AS003-unsafe-deserialization¶

    Unsafe deserialization via pickle or an unbounded yaml.load.

    Introduced in rigor-foundry/1.2.0.

    Why it matters. pickle and the default yaml.load reconstruct arbitrary objects from their input.

    How to verify. Deserialize only trusted local data, or switch to a bounded safe format (yaml.safe_load, JSON, or a schema-validated parser) for any externally sourced bytes.

    AS004-weak-hash-primitive¶

    Weak hash primitive md5 or sha1 in a possible security context.

    Introduced in rigor-foundry/1.2.0.

    Why it matters. md5 and sha1 are not collision resistant and must not back a security decision.

    How to verify. Confirm the digest is a non-security checksum; otherwise move to SHA-256 or a keyed MAC and record why the primitive is acceptable.

    AS005-insecure-temporary-file¶

    Insecure temporary file creation through tempfile.mktemp.

    Introduced in rigor-foundry/1.2.0.

    Why it matters. tempfile.mktemp returns a name with a race between the check and the later open.

    How to verify. Use tempfile.mkstemp or NamedTemporaryFile, which create the file atomically with a bound descriptor.

    AS006-js-dynamic-code-execution¶

    Native JavaScript or TypeScript dynamic code execution via eval or Function.

    Introduced in rigor-foundry/1.3.0.

    Why it matters. eval and the Function constructor execute a string as code, turning any tainted argument into arbitrary execution.

    How to verify. Replace the dynamic evaluation with an explicit parser, a lookup table, or a typed dispatch; if evaluation is unavoidable, prove the source is a trusted literal.

    AS007-go-command-execution¶

    Native Go external command execution via os/exec Command or CommandContext.

    Introduced in rigor-foundry/1.4.0.

    Why it matters. os/exec runs an external command, so a tainted argument can execute an unintended program or, with a shell, inject further commands.

    How to verify. Prove every argument is a trusted constant or validated allow-list value, pass an explicit argument vector, and never build the command from unsanitised input.

    AS008-rust-unsafe-block¶

    Native Rust unsafe block that suspends compiler memory-safety guarantees.

    Introduced in rigor-foundry/1.4.0.

    Why it matters. An unsafe block suspends the compiler's memory-safety guarantees, so a mistake inside it can cause undefined behaviour that safe Rust would have prevented.

    How to verify. Confirm the block is minimal, documents the invariants it upholds, and cannot be replaced by a safe abstraction; record why each unsafe operation is sound.

    AS009-c-unsafe-libc¶

    Native C or C++ call to an unbounded or command-executing libc function.

    Introduced in rigor-foundry/1.5.0.

    Why it matters. gets, the unbounded str/sprintf family, and system/popen are classic buffer-overflow and command-injection surfaces when their input is not strictly bounded and trusted.

    How to verify. Replace the call with a length-bounded equivalent (fgets, snprintf, strncpy with an explicit size) or an argument-vector exec, and prove the input is trusted and bounded.

    AS010-julia-unsafe-memory¶

    Native Julia unsafe_* intrinsic that bypasses bounds, type, and GC safety.

    Introduced in rigor-foundry/1.6.0.

    Why it matters. The unsafe_* intrinsics bypass Julia's bounds, type, and garbage-collection safety, so a bad pointer or length reads or writes arbitrary memory.

    How to verify. Confirm the pointer and length come from a live, correctly typed, GC-rooted object, or replace the intrinsic with a bounds-checked array or a safe wrapper.

    AS011-shell-eval-execution¶

    Native shell eval builtin that re-parses its argument as a command.

    Introduced in rigor-foundry/1.6.0.

    Why it matters. The shell eval builtin re-parses and executes its argument as a command, so any tainted value in that argument becomes an injected command.

    How to verify. Remove eval and call the command with an explicit argument vector, or prove every interpolated value is a trusted constant.

    AS012-disabled-tls-verification¶

    Python call that disables TLS certificate verification via verify=False.

    Introduced in rigor-foundry/1.7.0.

    Why it matters. verify=False disables certificate verification, so a network attacker can present any certificate and read or alter the traffic.

    How to verify. Restore verification (verify=True or a trusted CA bundle); if a self-signed host is truly required, pin its certificate instead of disabling verification.

    AS013-insecure-ssl-context¶

    Python use of ssl._create_unverified_context, which authenticates no peer.

    Introduced in rigor-foundry/1.7.0.

    Why it matters. ssl._create_unverified_context returns a context that accepts any certificate, so the peer is never authenticated.

    How to verify. Use ssl.create_default_context, or a context with an explicit trusted CA, so the peer certificate is verified.

    reliability¶

    RL001-bare-except¶

    Bare except clause that catches every exception and hides real failures.

    Introduced in rigor-foundry/1.8.0.

    Why it matters. A bare except catches every exception, including SystemExit and KeyboardInterrupt, so it hides real failures and blocks interruption.

    How to verify. Catch the specific exception types the block can actually handle, or re-raise after recording context; never swallow BaseException silently.

    RL002-mutable-default-argument¶

    Mutable default argument shared across calls, leaking state between invocations.

    Introduced in rigor-foundry/1.8.0.

    Why it matters. A mutable default argument is created once and shared across every call, so state leaks between invocations.

    How to verify. Default the parameter to None and create the list, dict, or set inside the function body, or confirm the shared instance is genuinely intended.

    supply-chain¶

    SC001-unhashed-pinned-requirement¶

    Pinned requirement in a hash-mode lock file carries no integrity hash.

    Introduced in rigor-foundry/1.9.0.

    Why it matters. A hash-pinned lock file records integrity digests for every dependency, but this pinned requirement carries none, so its artefact is installed without verification against tampering or index substitution.

    How to verify. Recompile the lock with hashes (for example pip-compile --generate-hashes) so every pinned requirement carries a --hash= digest, or justify why this dependency is exempt.

    SC002-vcs-url-requirement¶

    Dependency installed from a VCS checkout or URL, bypassing index hash pinning.

    Introduced in rigor-foundry/1.9.0.

    Why it matters. A dependency installed directly from a VCS checkout or a URL bypasses the package index and hash pinning, so the resolved artefact is mutable and unverified.

    How to verify. Pin the dependency to an immutable released version from the index with a recorded hash, or vendor and audit the exact revision if a direct source is genuinely required.

    container¶

    DK001-unpinned-base-image¶

    Dockerfile base image referenced by a mutable tag with no immutable digest.

    Introduced in rigor-foundry/1.10.0.

    Why it matters. A base image referenced only by tag is mutable, so the resolved image can change under the same Dockerfile and is never verified against a known digest.

    How to verify. Pin the base image to an immutable @sha256: digest (for example python:3.12-slim@sha256:...), or justify why a moving tag is required.

    DK002-root-runtime-user¶

    Dockerfile runtime stage sets no non-root USER, so the container runs as root.

    Introduced in rigor-foundry/1.10.0.

    Why it matters. The final image stage sets no non-root USER, so the container runs as root and a process escape keeps full root authority inside the namespace.

    How to verify. Add a USER directive selecting an unprivileged account (and create it if needed) as the last identity in the runtime stage, or justify the root run.

    data-privacy¶

    DP001-hardcoded-credential¶

    Credential-named variable assigned a string literal secret in tracked source.

    Introduced in rigor-foundry/1.11.0.

    Why it matters. A credential-named variable is assigned a string literal, so a secret is embedded in tracked source where it cannot be rotated and is exposed to everyone with repository read access.

    How to verify. Load the value from an environment variable or secret manager at runtime and remove the literal, or confirm it is a non-secret placeholder or fixture.

    DP002-embedded-private-key¶

    PEM private-key block embedded in tracked source, disclosing key material.

    Introduced in rigor-foundry/1.11.0.

    Why it matters. A PEM private-key block is embedded in tracked source, disclosing key material to everyone with repository read access.

    How to verify. Remove the key from source, rotate it, and load it at runtime from a secret store or an out-of-tree file that is never committed.

    documentation¶

    DC001-missing-license-header¶

    Tracked source owner lacks an SPDX licence identifier in its leading header.

    Introduced in rigor-foundry/1.12.0.

    Why it matters. A tracked source owner has no SPDX licence identifier in its leading header, so automated licence inventory cannot establish its declared licence.

    How to verify. Confirm the file's intended licence with the repository owner, then add the exact SPDX-License-Identifier header or record why the source is separately licensed.

    DC002-doc-version-drift¶

    Public package-version guidance differs from static PEP 621 project metadata.

    Introduced in rigor-foundry/1.12.0.

    Why it matters. A public README or documentation page names an explicit package version that differs from the repository's static PEP 621 project version.

    How to verify. Compare the statement with pyproject.toml [project].version, update current installation or compatibility guidance, or move genuinely historical text to a changelog or release-note surface.

    scientific¶

    SN001-exact-float-equality-in-test¶

    Python test uses exact equality against a direct floating-point literal.

    Introduced in rigor-foundry/1.13.0.

    Why it matters. A test compares a direct floating-point literal with exact equality, which can hide representation or tolerance assumptions.

    How to verify. Use a justified absolute/relative tolerance or prove exact binary identity is intended.

    SN002-unseeded-stochastic-test¶

    Python test uses a supported stochastic API before deterministic local seeding.

    Introduced in rigor-foundry/1.13.0.

    Why it matters. A supported stochastic API is used before deterministic local seeding, so repeated test outcomes may consume different samples.

    How to verify. Seed before the first draw or construct the local generator with a seed, then verify deterministic replay.

    operations¶

    OP001-print-in-library-code¶

    Python library code calls builtin print outside an intentional command surface.

    Introduced in rigor-foundry/1.14.0.

    Why it matters. Library code writes directly to process output, bypassing caller-controlled observability and output routing.

    How to verify. Replace incidental output with a returned value or structured logger, or prove the module is an intentional command boundary.

    OP002-credential-in-log-call¶

    Import-bound logging call receives a credential-named expression.

    Introduced in rigor-foundry/1.14.0.

    Why it matters. A credential-named expression is passed to an import-bound logging call and may disclose sensitive material.

    How to verify. Remove or redact the credential value before logging and verify captured logs contain only non-sensitive identifiers or digests.

    performance¶

    PR001-wall-clock-in-test¶

    Python test assertion reads an imported wall clock without explicit local control.

    Introduced in rigor-foundry/1.15.0.

    Why it matters. A test assertion reads a process wall clock without a recognised local freeze or dominating monkeypatch, so scheduling and clock movement can change its result.

    How to verify. Inject or freeze the clock at the assertion boundary, then replay the test with the exact controlled timestamp; retain a live-clock assertion only with bounded timing evidence and an explicit review.

    api-compatibility¶

    AA001-unbound-api-manifest¶

    Declared Python public surface differs from its tracked pinned manifest.

    Introduced in rigor-foundry/1.16.0.

    Why it matters (case 1 of 2: the declared public surface is not bound by the manifest). A declared Python public surface is not bound exactly by the tracked API manifest, so compatibility review cannot distinguish an intentional API edit from drift.

    How to verify (case 1 of 2: the declared public surface is not bound by the manifest). Review the declared names and downstream compatibility contract, then update rigor-public-api.json only when the exact public-surface change is intentional; do not infer a breaking change from unrelated source edits.

    Why it matters (case 2 of 2: the manifest is malformed or records a surface with no declaration). The tracked public API manifest is malformed or retains a surface with no matching literal declaration, so it cannot bind the repository's declared API state.

    How to verify (case 2 of 2: the manifest is malformed or records a surface with no declaration). Validate the versioned manifest schema and compare every recorded path with its exact module-level all; remove or update a row only after compatibility review.

    regulatory-readiness¶

    CR001-missing-disclosure-policy¶

    Explicit CRA scope lacks a tracked coordinated-vulnerability-disclosure policy.

    Introduced in rigor-foundry/1.17.0.

    Why it matters. Explicit CRA scope names a coordinated-vulnerability-disclosure policy that is not available as one tracked text file.

    How to verify. Confirm applicability, then add and independently review the declared tracked CVD policy; this candidate is not a compliance verdict.

    CR002-missing-security-contact¶

    Tracked coordinated-vulnerability-disclosure policy lacks a public contact signal.

    Introduced in rigor-foundry/1.17.0.

    Why it matters. The declared tracked CVD policy did not expose a syntactically bounded public contact address.

    How to verify. Review the complete public disclosure policy and verify a monitored public contact channel; aliases, routing, and response operation require independent evidence.

    CR003-stale-component-inventory¶

    Imported component inventory is not bound to the current repository state.

    Introduced in rigor-foundry/1.17.0.

    Why it matters. The newest imported component inventory is bound to a different exact repository state.

    How to verify. Review repository/SBOM drift and import a new externally generated SBOM only when appropriate; RIGOR-FOUNDRY does not generate an SBOM.

    CR004-untracked-reporting-timeline¶

    CRA event has a started reporting stage without a bound draft, receipt, or skip.

    Introduced in rigor-foundry/1.17.0.

    Why it matters (case 1 of 2: the declared CRA state is unreadable). Explicit CRA scope has no readable declared offline state, so reporting-stage evidence cannot be assessed.

    How to verify (case 1 of 2: the declared CRA state is unreadable). Bootstrap or recover the local ignored CRA evidence tree, then repeat the scan; absence is unresolved evidence, not a passing result.

    Why it matters (case 2 of 2: a reporting-stage clock has no bound draft, receipt or skip). An operational reporting-stage clock has an evidence anchor but no bound draft, receipt, or explicit already-provided skip.

    How to verify (case 2 of 2: a reporting-stage clock has no bound draft, receipt or skip). Recompute the exact offline timeline and inspect operator evidence; only the manufacturer decides applicability and performs any submission.

    CR005-support-period-too-short¶

    Declared support period below 60 months lacks a supported shorter-use relation.

    Introduced in rigor-foundry/1.17.0.

    Why it matters. The declared support period is below 60 months and no internally consistent shorter expected-use relation currently supports it.

    How to verify. Verify the product's reasonably expected use time and retained evidence against the current official act; a below-60 declaration is not by itself a legal failure.

    CR006-fixed-vuln-without-advisory¶

    Fixed-vulnerability state lacks publication or justified-delay evidence.

    Introduced in rigor-foundry/1.17.0.

    Why it matters. Operator-declared fixed-vulnerability state lacks a verified advisory publication record or justified-delay review record.

    How to verify. Inspect the fixed-vulnerability and security-update evidence, then bind only operator-confirmed publication or justified-delay records; RIGOR-FOUNDRY never publishes automatically.

    github-actions¶

    GA001-unpinned-action-reference¶

    Executable action or reusable workflow reference lacks an immutable pin.

    Introduced in rigor-foundry/1.19.0.

    Why it matters. An executable action or reusable workflow reference lacks a full commit or image digest.

    How to verify. Inspect the action owner and exact upstream object, then pin a reviewed full commit SHA or Docker SHA-256 digest. Local repository actions do not need external revision pins.

    GA002-run-context-interpolation¶

    Run script directly interpolates untrusted event, branch or input data.

    Introduced in rigor-foundry/1.19.0.

    Why it matters. A run script directly interpolates event data, a branch name or an input.

    How to verify. Trace the exact trigger and value into the generated script. Prefer an intermediate environment variable with shell-appropriate quoting. This signal is not an exploit proof.

    GA003-pull-request-target-checkout¶

    Target-event checkout selects PR code or an unresolved dynamic source.

    Introduced in rigor-foundry/1.19.0.

    Why it matters. A pull_request_target checkout selects PR code or an unresolved dynamic source.

    How to verify. Review token permissions, secrets, downstream execution and the checkout version's fork protections, including allow-unsafe-pr-checkout. Prefer trusted base checkout; this configuration candidate does not prove that untrusted code was executed.
